# Аналитика и fact-agent

## Фэнтези-оценка

Фэнтези-вклад считается на уровне `игрок × карта × метрика`. Коэффициент
эмблемы умножает базовый вклад метрики; качества и свойства меняют именно
бонус эмблемы согласно правилам клиента. Роль игрока берётся из нормализованных
roster/match данных, а не из случайного игрового никнейма.

Для составных фэнтези-слотов используются:

- `core_pair` — среднее игроков позиций 1 и 3;
- `mid_single` — игрок позиции 2;
- `support_pair` — среднее игроков позиций 4 и 5.

Правило итогового периода клиента «две лучшие карты лучшей серии» не следует
подменять средним по всем картам. Для исследования ceiling, p75, стабильности
и риска храните и отображайте их отдельно.

## Основные аналитические вопросы

База поддерживает ранжирование игроков, пар ролей и комбинаций метрик по
среднему, максимуму, p75, покрытию и предсказуемости. Для рекомендаций
используйте p75 как ориентир потенциала без чрезмерной зависимости от единичных
выбросов, а среднее и coverage — как проверку устойчивости.

Модели prediction/reliability/optimizer из ранних экспериментов не являются
дефолтным production API. Их отчёты в `reports/` полезны только как
воспроизводимые результаты конкретных прогонов.

## Статистические и ML-слои

### Описательная аналитика

Базовый слой намеренно не является нейросетью. Для `игрок/role slot x stat`
он считает mean, max, p75, non-zero coverage, variance и связь метрик. P75
используется как компромисс между ceiling и единичным выбросом. Для выбора
нескольких эмблем дополнительно рассматриваются корреляции: высокий farm и
короткая игра могут быть структурно несовместимыми источниками очков, даже если
по отдельности выглядят сильными.

### Prediction baselines

| Метод | Зачем нужен | Ограничение |
|---|---|---|
| Segment mean | нижняя планка: среднее по сегменту роли/стадии | не различает игроков |
| Ridge regression | линейная, интерпретируемая связь признаков и fantasy target | плохо ловит сложные взаимодействия |
| Quantile regression | оценка p75/ceiling вместо только среднего | чувствительна к малой выборке |
| GBDT/ranking | нелинейные признаки, ранжирование кандидатов | требует строгого temporal split |
| Monte Carlo rescoring | распределение возможного результата и риск profile | зависит от калибровки распределений |

Оценки не переносятся автоматически между EWC и TI: различаются составы,
стадии и полнота support-метрик. Любой отчёт обязан указывать event, split,
target и модель.

### Метрики качества

- `MAE`: средняя абсолютная ошибка численного fantasy target; ниже лучше.
- Spearman: совпадение порядка игроков/слотов; ближе к `1` лучше.
- `NDCG@k`: качество верхней части рейтинга; `1` означает идеальный порядок
  top-k, а случайный baseline обычно заметно ниже.
- Interval coverage: доля фактических значений внутри предсказанного интервала;
  проверяет калибровку, а не только точность точки.

Данные следует разделять по времени или целым сериям/матчам. Случайный split
строк `игрок x карта` может давать утечку: похожие карты одного игрока окажутся
и в train, и в test.

## Правило source-first

Agent обязан сначала определить, достаточно ли SQLite. Если факт есть в базе,
ответ строится SQL-запросом с понятными полями и без выдуманных чисел. Если
факта нет, agent должен обозначить это и предложить конкретный источник или
процедуру обогащения. Внешний LLM может форматировать ответ, но не заменяет
извлечение фактов.
